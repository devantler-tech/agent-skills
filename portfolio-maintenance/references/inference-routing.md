# Delegation under an inference-routing contract

Use this procedure only when the consumer declares **Inference routing** and the selected work needs
delegation or escalation. The consumer supplies model assignments and operational limits; the
delivery owner retains the `portfolio-maintenance` skill's mandatory survey, trust, ownership, and
promotion gates. A child performs only its assigned packet; it does not start another portfolio run.

Delegate only a coherent, independently verifiable deliverable when expected savings exceed
instruction/history loading, tool use, parent integration, retries, and escalation. Keep deterministic
lint, formatting, tests, and Git commands in the task doing the associated work; do not spawn another
agent solely to run one of them. A builder may commit its scoped changes in its own isolated working
copy to produce a result revision. Preserve required instructions; a short handoff does not bound
automatically injected history or preloaded skills.

**One live delivery owner per work item.** The owner manages the claim and PR lifecycle, integrates
child results, and verifies the complete promotion gate. Each active builder gets a physically isolated
working copy and explicit non-overlapping scope; serialize coupled changes even when their paths
differ. Every child, including a builder, needs verified runtime enforcement of permitted paths,
tools and remote actions across shell, MCP and authenticated forge access. Read-only children must
also be unable to write. A role name, prompt, or isolated directory does not enforce those boundaries.
Consumer survey overrides still apply; unavailable delegated enforcement retains the supported inline
path without skipping discovery.

Give each child a bounded task packet: repository and immutable base revision; work item and live owner;
renewable owner claim token/generation and expiry;
contract and routing-policy revisions; permitted paths and tools; acceptance checks; execution and
escalation bounds; and the evidence needed to resume. The child returns its result revision, checks
and outcomes, unresolved findings, and a complete/partial/blocked status. It does not independently
publish or merge the work. The owner verifies the actual result rather than trusting a completion
message. If a child-local commit cannot be transferred, return a portable patch/artifact with its
base revision and integrity digest; the owner applies and verifies it before producing the integration
commit. Branch publication and the PR lifecycle remain with the delivery owner. Rebind ownership
before resumed mutations and stop the former writer before a handoff;
passing context to another runtime does not transfer ownership or subscription entitlement. The
runtime must deny further child mutations when the owner's claim expires or is lost, and stop/cancel
the stale child. The owner revalidates that same fence before accepting a result; a takeover cannot
accept stale-owner output merely because its checks pass. If claim-bound execution/cancellation is
unavailable, retain inline work rather than allowing an orphaned writer.

Escalate only on the consumer's declared failure evidence or direct task classification. Carry the
failed checks and distinct attempted hypotheses forward. Authentication, permission, quota, tool,
ownership, and missing-authority failures need operational recovery or a decision, not a larger model.
Never widen billing, model, tool, or concurrency limits during recovery. Retain the parent/child attempt
chain and measured context costs through the consumer's telemetry for `agent-improvement`.
